# commandress security audit — 2026-05-18

**Scope**: v0.8.0 codebase (commit at the moment of audit) — `src/`, `adapters/`, `scripts/`. **Stdlib (`lib/`)** is out of scope as a vendored snapshot; relevant findings against stdlib code are documented as upstream issues to file with Cyrius.

**Methodology**: dual-track — (a) internal sweep of the codebase against a 7-surface threat model (env-var input, subprocess exec, file I/O, fixed-size buffers, cache attacks, ANSI escape injection, parser DoS); (b) external research on CVEs and 0day-class advisories from 2020–2026 for adjacent tools (starship, fish git-prompt, oh-my-zsh themes, p10k, terminal emulators). Findings cross-reference both tracks so each entry has a published-CVE precedent or an explicit "no published CVE in the search window" qualifier.

**Outcome**: **6 findings to fix in v0.9.0** (F-1 ANSI sanitization; F-3 cache dir mode-verify; F-4 cache reads O_NOFOLLOW; F-5 cache writes atomic; F-7 bounded exit-code parse; F-8 PATH-walker reject relative). **2 findings deferred** (F-2 sit hooks surface — upstream sit work; F-6 TOML parser depth bound — upstream stdlib work). **4 informational** (F-9..F-12 — defensive design verifications + adapter contract clarification).

---

## Threat model

`cmdrs` runs on every prompt redraw — single-process, short-lived, no persistent daemon. The prompt-render surface is:

```
shell ──fork+exec──> cmdrs ──read─→ ~/.commandress (user-controlled config)
                          ──read─→ env vars (HOME, $AGNOSHI_LAST_EXIT, PATH, VIRTUAL_ENV, USER)
                          ──read─→ getcwd, files (.python-version, .nvmrc, rust-toolchain, VERSION)
                          ──fork+exec→ sit status / cyrius --version (per cache TTL)
                          ──read/write─→ /tmp/commandress-<uid>/<seg>-<hash>
                          ──emit─→ stdout (ANSI SGR + raw text)
shell ──capture stdout──> paint as prompt (re-emit every redraw)
```

Three attacker positions are realistic:

1. **Hostile project a user `cd`s into** — controls `cyrius.cyml`, `VERSION`, `.python-version`, `.nvmrc`, `rust-toolchain`, `.sit/HEAD`, `.sit/config`, and any branch name. Can place arbitrary bytes in any of these.
2. **Co-tenant on the same host (same `/tmp`)** — different UID, no privilege boundary to `cmdrs`'s UID, but can pre-create `/tmp/commandress-<uid>/` with permissive mode or symlink-swap cache files.
3. **Process that controls the calling shell's env** — sets `$AGNOSHI_LAST_EXIT`, `$VIRTUAL_ENV`, `$USER`, `$HOME`, `$PATH` to values designed to subvert the segment outputs.

`cmdrs` does **not** run setuid, has no privilege boundary to cross, and never invokes a shell-interpreted command line — those eliminate whole CVE classes upfront (Shellshock CVE-2014-6271, sudo Baron Samedit CVE-2021-3156). The realistic impact ceiling across all findings is **terminal-state corruption + info leak in cached state**. No RCE path was identified in the audited code paths, but the terminal-emulator CVEs in §F-1's references (CVE-2022-45872 iTerm2; CVE-2022-44702 Windows Terminal; CVE-2024-56803 Ghostty) demonstrate that **emitting attacker-controlled ANSI escapes to a sufficiently-buggy emulator IS an RCE channel** — so F-1's sanitization closes that bridge regardless of which emulator the user runs.

## Findings

### F-1 — ANSI / C0-control injection in segment content [HIGH]

**Where**: every segment that copies bytes from a source outside `cmdrs`'s own configuration:

- `src/segments/vcs.cyr::vcs_parse_render` — copies branch name verbatim between `On branch ` and the next `\n`.
- `src/segments/python_env.cyr::python_env_basename` — returns the bytes after the last `/` of `$VIRTUAL_ENV`.
- `src/fslookup.cyr::read_trimmed_file_at` — returns trimmed bytes of `<root>/VERSION` / `.python-version` / `.nvmrc` / `rust-toolchain`.
- `src/segments/user.cyr` — `$USER` fallback emitted as-is.
- `src/segments/cyrius_env.cyr::cyrius_env_parse_version` — copies the version string after `cyrius ` from the subprocess output.
- `src/segments/cwd.cyr` — `getcwd(2)` bytes, plus `$HOME` for shortening. (getcwd's output is filtered by the kernel — unprintable bytes in directory names are unusual but not impossible; `$HOME` is more dangerous since it's env-derived.)

**Threat**: an attacker who controls any of these source values can inject ESC (`0x1b`) or other C0 control bytes. The prompt re-emits these every keystroke. Demonstrated CVE exploits include:

- **CVE-2024-52005** (Git, 2024, CVSS 7.5) — sideband channel emitted ANSI to stderr without filtering. Direct precedent for the vcs segment + sit output.
- **CVE-2024-50349** (Git, 2024) — URL-decoded host names with embedded ANSI in credential prompts → phishing.
- **CVE-2021-3934** (oh-my-zsh themes, 2021) — git branch names containing `%`-sequences executed via zsh `print -P`.
- **CVE-2024-56803** (Ghostty, 2024-12) — title injection → RCE on emulator-level bug.
- **CVE-2022-45872** (iTerm2 DECRQSS, 2022) — terminal-emulator RCE via crafted escape, CVSS 9.8.
- **CVE-2022-44702 / 47583 / 45063 / 46387 / 4170 / 23465 / 46663 / 39150 / 39726** (the dgl.cx 2023 set) — 10 emulator CVEs across iTerm2, Windows Terminal, mintty, xterm, ConEmu, rxvt-unicode, SwiftTerm, less — all triggerable by ESC-bearing bytes reaching the terminal.
- **GHSA-76r7-hhxj-r776** (Rails ActiveRecord, 2024) — column/table names with ANSI in SQL log output.
- **CVE-2055-55754** (Apache Tomcat, 2025) — same class in console log output.
- **OpenAI Codex CLI** ([writeup](https://dganev.com/posts/2026-02-12-ansi-escape-injection-codex-cli/), 2026) — ANSI-from-data into a terminal that's an AI agent's working surface → RCE.

**Mitigation (v0.9.0)**: introduce a `_sanitize_segment_output(s)` helper that copies the input cstring while skipping bytes < `0x20` (allowing `\t`? — probably no, prompts don't legitimately use tabs in segment content) and `0x7F` (DEL). Apply in `src/render.cyr` between dispatcher return and SGR-wrapped emit; segment SGR wrappers themselves remain untouched because they come from `_sgr_for(cfg, name)` and `cfg_separator_glyph` — both config-derived, both trusted.

**Acceptance**: a test that fabricates a `vcs_parse_render` input with `On branch evil\x1b[2J\n` and asserts the rendered output strips the `\x1b[2J`. Plus smoke for `$VIRTUAL_ENV=/path/with/\x1bevil`.

### F-2 — VCS segment inherits sit's repo-local-config execution surface [HIGH, DEFERRED]

**Where**: `src/segments/vcs.cyr::vcs_render` shells out to `sit status` inside the user's cwd. If a hostile project's `.sit/config` (or sit's equivalent) supports hook execution / fsmonitor / filter-config-by-pattern, those run as the user's UID whenever `cmdrs` invokes sit — i.e. every prompt redraw inside the attacker's tree.

**Threat**: direct precedent in **CVE-2022-20001** (fish, 2022) — fish's git-prompt invoked `git status` inside attacker-controlled directories; malicious `.git/config` `fsmonitor` hook executed arbitrary code. **starship issue #3974** (open) notes that starship is still in this class — upstream guidance is to invoke git with `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null GIT_CONFIG_NOSYSTEM=1 -c core.fsmonitor=false -c core.hooksPath=/dev/null -c protocol.version=2`.

**Current state**: `shellout_capture(sit_path, argv, envp=[NULL], ...)` passes an *empty* environment to the sit child. That kills `$GIT_CONFIG_*`-style env injection. But it does *not* prevent sit from reading the repo-local `.sit/config` and acting on its declarations (hooks, fsmonitor analogues) — that decision is sit-internal.

**Mitigation**: requires upstream sit work — sit needs a `--no-hooks --no-fsmonitor --no-extensions` flag (or equivalent safe-mode) that `cmdrs` then passes. **Filed as a deferred audit item**, not fixed in v0.9.0. Tracking: this audit doc + ADR 0004 amendment proposed.

**Acceptance for future fix**: once sit ships a safe-mode flag, `vcs_render` adds it to argv; this audit item promotes to v?.?.0 closure.

### F-3 — Cache directory pre-existence + mode not verified [MEDIUM]

**Where**: `src/cache.cyr::cache_init` calls `sys_mkdir(dir, 0o700)` and ignores the return. If `/tmp/commandress-<uid>/` exists with a permissive mode (e.g. `0o777` — pre-created by an attacker who knew the victim's UID and the path naming convention), our cache files written with `file_write_all` (mode `0o644`) become world-readable. The cached values are vcs branch names and cwd hashes — information leak.

**Threat**: **CVE-2023-33865** (RenderDoc, 2023) — `/tmp/RenderDoc` reused without dir-perm verification. **CVE-2026-31979** (Himmelblau, 2026) — Kerberos cred cache in shared `/tmp` without owner check → privilege escalation. **GHSA-w853-jp5j-5j7f** (py-filelock, 2024) — TOCTOU between `stat` and `open`.

**Mitigation (v0.9.0)**: after `sys_mkdir`, `sys_stat` the dir; verify `st_uid == sys_getuid()` and `(st_mode & 0o777) == 0o700`. On mismatch, set a module-level flag that disables `cache_get` / `cache_put` for this invocation (each becomes a no-op). The vcs segment then falls back to its uncached path — slow but safe.

**Acceptance**: a test that pre-creates `/tmp/commandress-<TEST_UID>/` with `0o777` and verifies `cache_get` returns 0 (cache disabled) regardless of file content.

### F-4 — Cache reads follow symlinks (no `O_NOFOLLOW`) [MEDIUM]

**Where**: `src/cache.cyr::cache_get` calls `file_open(path, 0, 0)` which is bare `O_RDONLY` — follows symlinks.

**Threat**: same class as F-3. **GHSA-w853-jp5j-5j7f** (py-filelock, 2024) — symlink-swap TOCTOU between `stat` and `open`. With F-3 fixed, the dir is verified owner+mode but individual cache files inside aren't — an attacker who briefly had write access (e.g. before F-3's mode-check, on a system that doesn't enforce sticky bit) could symlink a cache file to `/etc/shadow` (readable as us; but cache reads only happen if mtime is fresh — limited window).

**Mitigation (v0.9.0)**: change `file_open(path, 0, 0)` to `file_open(path, O_NOFOLLOW, 0)`. If a symlink swap occurred, `open` fails → `cache_get` returns 0 → segment falls back to the real probe + writes a fresh cache file.

**Acceptance**: a test that creates a symlink `/tmp/commandress-<TEST_UID>/vcs-deadbeef → /etc/passwd`, calls `cache_get("vcs", <matching cwd>, 1)`, and asserts the return is 0.

### F-5 — Cache writes are not atomic [MEDIUM]

**Where**: `src/cache.cyr::cache_put` calls `file_write_all` which opens with `O_WRONLY | O_CREAT | O_TRUNC`. Between `O_TRUNC` and the write, a co-uid process could read a half-written file (low impact — partial cstring is just a shorter branch name), or — worse, with `O_NOFOLLOW` not yet on `file_write_all` — a symlink-swap attack succeeds.

**Threat**: same class as F-3 / F-4. Atomic-write-via-rename is the canonical fix.

**Mitigation (v0.9.0)**: open `<path>.tmp.<pid>` with `O_WRONLY | O_CREAT | O_EXCL | O_NOFOLLOW` (mode `0o600`), write, then `rename(<tmp>, <path>)`. `rename(2)` is atomic on POSIX. On `EEXIST` (concurrent `cmdrs` write), unlink stale tmp and retry once; if still fails, skip caching this redraw (next redraw retries). Tighten mode to `0o600` since dir is `0o700` anyway.

**Acceptance**: tests that `cache_put` works under normal conditions (verified by `cache_get` returning the bytes); a stress test that races two concurrent `cache_put`s and verifies the final cache file is intact (not torn).

### F-6 — TOML parser DoS surface from user-controlled config [MEDIUM, DEFERRED]

**Where**: `~/.commandress` is parsed by `lib/toml.cyr::toml_parse` (stdlib). Up to **64 KB** of user-controlled bytes are read into the parser via `config_load`. If the parser doesn't bound recursion depth, deeply-nested `[[[[…]]]]` arrays could stack-overflow.

**Threat**: **CVE-2023-3894** (Jackson Java TOML, 2023, `StackOverflowError` on deeply-nested input). **toml-rs issue #206** (no CVE, 2021) — 20,000-bracket SO in `toml_edit`. **PEP 680 / tomllib docs**: *"a malicious TOML string may cause the decoder to consume considerable CPU and memory resources."*

**Current state**: `lib/toml.cyr` is part of the Cyrius stdlib snapshot; reviewing its depth-handling is outside this audit's `src/` scope. The 64 KB read cap in `config_load` is a soft bound but is itself somewhat large.

**Mitigation (deferred)**: file an upstream Cyrius stdlib issue requesting a documented recursion / array-depth cap (suggest 32 levels) on `toml_parse`. Tighten the read cap in `config_load` from 64 KB to ~16 KB (a real config is ~1 KB; 16 KB is generous). The byte-cap fix is small and *can* land in 0.9.0; the parser-depth fix waits for stdlib. **Decision**: ship the byte-cap fix as part of F-6 in 0.9.0; document the upstream gap.

**Acceptance**: test reading a 100 KB config returns defaults (load fails fast). Upstream filing tracked separately.

### F-7 — `atoi(getenv("AGNOSHI_LAST_EXIT"))` unbounded [LOW]

**Where**: `src/main.cyr::main` reads `$AGNOSHI_LAST_EXIT` via `atoi`. No length cap, no range clamp.

**Threat**: closest published-pattern is **CVE-2019-14287** (sudo, 2019) — integer wrap of attacker-influenced numeric input. For `cmdrs` the impact is much smaller (no privilege crossing): worst case is a `[<very large number>]` rendered in the prompt, or `0` on overflow truncation. Documented for hygiene rather than risk.

**Mitigation (v0.9.0)**: cap `strlen($AGNOSHI_LAST_EXIT)` at 10 characters (`INT32_MAX` is 10 digits) before atoi. Optionally clamp the parsed value to `[0, 65535]` (POSIX exit range × signal-killed status). Trivial — ~5 LoC.

**Acceptance**: test passing `AGNOSHI_LAST_EXIT="9999999999999999999999"` produces a bounded numeric output, not garbage.

### F-8 — `find_in_path` allows relative `$PATH` entries [LOW]

**Where**: `src/pathlookup.cyr::find_in_path` walks `$PATH` colon-separated. Currently skips empty entries (`dir_len == 0`) but does **not** check that each entry is absolute. A `$PATH` containing `bin` or `.` would produce candidates like `bin/sit` and run them if executable from cwd.

**Threat**: historic sudo "`.` in `PATH`" pattern. The user's `$PATH` is the user's risk in general, but `find_in_path` is specifically designed for subprocess invocation — defense-in-depth says skip non-absolute entries.

**Mitigation (v0.9.0)**: in the walk loop, require `path[pi] == '/'` before building the candidate. Skip any entry that doesn't start with `/` (including `.`, `..`, and unqualified names).

**Acceptance**: test with `PATH=":.:/usr/bin"` finds `sh` in `/usr/bin` while skipping the empty entry and the `.`.

### F-9 — 32-bit hash collision space in cache keys [INFO]

`src/cache.cyr::_cache_hash` is djb2 32-bit. Birthday-paradox at ~65 K distinct keys; users have at most a few thousand cwds. Acceptable. Documented.

---

### F-10 — Subprocess argv is hardcoded, not user-influenced [INFO]

`vcs_render` and `_cyrius_env_shellout` build argv in code (`["sit", "status"]`, `["cyrius", "--version"]`). No path for user input to influence argv. By-design verified.

---

### F-11 — Cache file mode `0o644` inside `0o700` dir [INFO]

Defense-in-depth: dir perms protect file readability today. F-5's mitigation tightens file mode to `0o600` as a side effect of using `O_CREAT | O_EXCL | O_NOFOLLOW` with explicit mode. After F-5 lands, this finding is moot.

### F-12 — Adapter contract: consumer must not re-expand `cmdrs` output [CONTRACT]

`cmdrs` emits raw bytes including ANSI SGR escapes. If a shell adapter or a future agnoshi prompt-cmd consumer re-runs the bytes through a percent-expansion / variable-expansion pass, attacker-injected `%` / `$` / `` ` `` / `\` sequences (from segment content sources in F-1) could trigger code execution.

**Threat**: **CVE-2021-3934** (oh-my-zsh `print -P`) — branch names containing `%`-sequences executed via zsh prompt-percent expansion. **CVE-2021-45444** (zsh `PROMPT_SUBST` recursion) — recursive expansion of `%F{...}` arguments → RCE.

**Current state**:

- **zsh adapter**: sets `prompt_subst` which evaluates `$(...)` *once*. Single non-recursive pass — safe.
- **bash adapter**: assigns `PS1` to the captured `cmdrs | sed`-wrapped output. bash does not auto-percent-expand. Safe.
- **agnoshi adapter**: contract-only. Spec must explicitly forbid re-expansion.

**Mitigation (v0.9.0)**: extend `adapters/agnoshi.sh`'s header contract with an explicit rule: *"agnoshi MUST treat `cmdrs` output as a literal byte string for terminal emission. It MUST NOT pass through any percent-expansion, variable-expansion, backtick-evaluation, or other shell-syntax pass. The bytes go straight to the terminal."* Combined with F-1's sanitization of segment content, this closes the chain.

**Acceptance**: documentation amendment; no code change needed in v0.9.0 (zsh + bash adapters already comply).

## Out of scope

- **`lib/` stdlib code review** — vendored snapshot from Cyrius 5.11.64. Stdlib hardening is the toolchain owner's responsibility; we audit our consumption patterns only.
- **Cross-arch audit (aarch64 / macOS)** — commandress is x86_64-Linux today (per AGNOS targeting). Same-codebase review for other arches lands when those targets ship.
- **Fuzzing harness for the segment parsers and config loader** — out of v0.9.0 scope. `tests/commandress.fcyr` is a stub today; growing it is a v0.9.x or v1.0.x bite.
- **Side-channel timing analysis** — `cmdrs` doesn't process secrets. No timing-sensitive code paths. No analysis required.
