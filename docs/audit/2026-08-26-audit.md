# commandress P-1 audit — 2026-08-26

**Scope**: the v1.1.5 codebase — `src/` (all 21 first-party modules, 2,594 lines),
`adapters/`, `scripts/`, `.github/workflows/`, `cyrius.cyml`. The vendored `lib/`
snapshot stays out of scope as a dependency artifact, **except** how our code calls
into it (wrong arity, ignored returns, misused contracts) and except `lib/cmdit.cyr`,
which arrived at 1.1.5 and had never been audited from the consumer side.

**Prior report**: [2026-05-18](2026-05-18-audit.md) (v0.8.0 baseline — F-1 ANSI
sanitization, F-3 cache-dir mode verify, F-4 `O_NOFOLLOW`, F-5 atomic temp+rename,
F-7 bounded exit parse, F-8 absolute-only PATH walk, all shipped in v0.9.0).

**Method**: dual track. (a) A five-dimension parallel read of the first-party code
(memory/buffer discipline, untrusted input reaching the terminal, the new cmdit CLI
surface, cache/filesystem/TOCTOU/subprocess, supply chain + CI + scripts), with every
candidate finding then handed to an adversarial reviewer whose default posture was
that the claim is wrong. (b) **Live attack testing against the built binary** — real
hostile inputs through real shells, not reasoning about what the code should do.

Track (b) is what found the one serious issue, and it is also what killed several
plausible-looking ones. Both directions are reported below.

**Numbering**: findings carry two prefixes because the two tracks ran independently and
the source comments cite them. **P-nn** came from the direct/manual track (b); **A-nn**
from the parallel-read track (a). Neither series is "more real" than the other — both
were adversarially verified, and both produced HIGHs the other missed.

**Outcome**: **4 HIGH**, **3 MEDIUM**, **12 LOW**, **2 INFO** confirmed. All fixed in
v1.1.6 except the accepted gaps recorded at the end. Suite **295 → 304**.

The two tracks caught different things, which is the argument for running both:

- The manual track found **P-01** (both shell adapters executing prompt content) by
  reading `adapters/zsh.sh` and then *trying the attack*. No amount of reading `src/`
  would have found it — the defect is in the shell glue, and `cmdrs` itself is correct.
- The parallel read found **A-01** (a FIFO in a hostile repo hangs the prompt forever),
  which I had walked straight past: I fuzzed the *contents* of those probe files and
  never questioned their *file type*.
- The parallel read also found **A-02**, a second watchdog hang that my own P-05 test
  had missed. I tested the buffer-full path, proved it safe, and generalised — wrongly —
  to the whole function. The EOF-with-live-child path was still open. **P-05's "verified
  safe" conclusion was correct for the case tested and too broad as stated**; that is
  corrected below.
- And it found **A-03**: the CI lock guard added earlier the same day was *inert*,
  because an earlier workflow step overwrote the file it compared against.

---

## Threat model

Unchanged from 2026-05-18 in shape — `cmdrs` runs on every prompt redraw, single
process, short-lived, not setuid, no privilege boundary to cross — with one surface
added since: the CLI is now parsed by cmdit, and the toolchain is installed in CI by
a piped remote script.

The three attacker positions that matter:

1. **A hostile project directory** the user merely `cd`s into. Controls `cyrius.cyml`,
   `VERSION`, `.python-version`, `.nvmrc`, `rust-toolchain`, and any `sit` branch name.
2. **A co-tenant on the same host** — different UID, can attempt to pre-create or
   symlink-swap under `/tmp`.
3. **A hostile environment** — controls `HOME`, `PATH`, `USER`, `VIRTUAL_ENV`,
   `AGNOSHI_LAST_EXIT`.

The impact ceiling assumed by the previous audit was "terminal-state corruption + info
leak". **P-01 raises that ceiling to arbitrary command execution**, and the mechanism
was not in `cmdrs` at all — it was in the shell glue that consumes its output.

## Findings

### P-01 — both shipped shell adapters executed attacker-chosen commands, every redraw · HIGH

**Where**: [`adapters/zsh.sh`](../../adapters/zsh.sh) (`setopt prompt_subst`),
[`adapters/bash.sh`](../../adapters/bash.sh) (bash's `promptvars`, on by default).

**Mechanism**. `cmdrs` renders bytes it does not choose — a branch name, the contents
of `.python-version` / `.nvmrc` / `rust-toolchain` / `VERSION`, `$VIRTUAL_ENV`. F-1
strips control bytes at the render chokepoint, and it does so correctly (verified —
see *Verified clean*). But `$`, `(`, `)` and `%` are ordinary printable characters:
F-1 passes them through, as it must, because they are legal in a branch name.

The adapters then handed that string to the shell **as a script**:

- `zsh.sh` ran `setopt prompt_subst`, which tells zsh to perform command substitution
  on the prompt at every redraw.
- `bash.sh` inherited `promptvars`, on by default, which applies parameter expansion
  **and** command substitution to `PS1`.

**Failure scenario, executed rather than argued.** A repository containing:

```sh
printf '$(touch /tmp/PWNED_MARKER)\n' > .python-version
```

`cmdrs` renders it (correctly) as the literal text `$(touch /tmp/PWNED_MARKER)`.
Sourcing `adapters/zsh.sh` and `cd`-ing into that directory then produced:

```
PROMPT raw bytes: \033[33m$(touch /tmp/PWNED_MARKER)\033[0m $
RESULT: MARKER CREATED — command executed
```

Confirmed identically under bash (`shopt -p promptvars` → `shopt -s promptvars`;
`PS1` expansion created the marker). Every keystroke-triggered redraw re-executes it.

**Why this is the whole ballgame**: the project already knew the rule. `adapters/agnoshi.sh`
states it in its 5-point contract — *"bytes are a LITERAL PROMPT STRING. agnoshi MUST
NOT pass them through percent-expansion, variable-expansion, backtick-eval"* — citing
CVE-2021-45444, and the 2026-05-18 audit recorded it as F-12. The rule was written for
the adapter that does not exist yet, and violated by the two that ship.

Same class as **CVE-2021-3934** (oh-my-zsh: git branch names via `print -P`) and
**CVE-2021-45444** (zsh `PROMPT_SUBST`).

**Fix (v1.1.6)**:
- zsh: `setopt prompt_subst` removed. It was never needed for this design — `PROMPT`
  is assigned from `$( )` inside the `precmd` hook, so by render time it already holds
  finished bytes; there is no `$(cmdrs)` left to expand. The option bought nothing and
  opened the hole. Verified: with it removed, the marker is not created.
- zsh: `%` is a **separate** channel — zsh expands `%` prompt escapes whether or not
  `prompt_subst` is set — so segment content is now `%`-doubled (`${_l//\%/%%}`).
  Verified: `ab%(?.X.Y)cd%B` renders literally instead of collapsing to `abXcd`.
- bash: `shopt -u promptvars`. Verified: blocks the execution.
- Both fixes carry the rationale inline, and `adapters/README.md` gained a *"the prompt
  string is DATA, not a script"* section with a per-shell rule table and a two-line
  reproduction so a future adapter author can self-test.

**Stated trade-off**: `shopt` is shell-global, so sourcing `bash.sh` disables
`promptvars` for the whole session. A user whose own `PS1` relies on `$(...)` being
expanded at render time loses that. That is the correct trade — the alternative leaves
an execution channel open — and it is documented in `adapters/README.md` rather than
left to be discovered.

### A-01 — a FIFO in a hostile project directory hangs the prompt forever · HIGH

**Where**: [`src/fslookup.cyr`](../../src/fslookup.cyr) `read_trimmed_file_at`, and
[`src/config.cyr`](../../src/config.cyr) `config_load`.

Both read external files with `file_read_all`, which opens with a plain
`open(path, O_RDONLY)`. **On a FIFO with no writer, `open(2)` blocks indefinitely** —
and nothing in this program covers that: the only watchdog is `shellout_capture`'s epoll
deadline, which wraps fork+exec, not file reads, and `main()` installs no alarm. The
candidate is selected by `find_ancestor_with`'s `access(F_OK)`, which succeeds on a FIFO.

**Failure scenario, reproduced on all five reachable paths.** A repo shipping `VERSION`,
`.python-version`, `.nvmrc` or `rust-toolchain` as a FIFO — and **tar preserves FIFOs**,
so extracting an archive or cloning is enough — hangs `cmdrs` forever:

```
$ mkfifo VERSION && timeout 6 cmdrs ; echo $?
124          # never printed a byte, never returned
```

`/proc/<pid>/wchan` on the hung process reads `wait_for_partner` — the kernel's
`fifo_open` wait. `PROMPT="$(cmdrs)"` never completes, so the user has no prompt and no
input loop until they kill it. `~/.commandress` itself is the fifth path, reachable from
a hostile `HOME`.

This is the "renderer must never block the shell" failure, with **no timeout anywhere on
the path**. It outranks P-01 on reachability: it needs no adapter and no shell feature,
just `cd`.

**Fix**: a `read_regular_file` helper — `O_NONBLOCK` on the open, then `fstat` on the
*already-open fd* requiring `S_IFREG`, then read from that fd. Two guards because either
alone is insufficient: `O_NONBLOCK` stops the open from parking, and the `S_IFREG` gate
additionally rejects device nodes whose *reads* stall (`/dev/zero` would read forever
into our cap). Checking the open fd rather than the path also closes the TOCTOU between
the `access(F_OK)` that selected it and the open.

**AGNOS**: guarded off, deliberately, and this was not obvious. `O_NONBLOCK` is defined
only in the Linux/macOS syscall peers — naming it would fail the `--agnos` build — and
agnos's `sys_fstat` is a hard stub returning `-1`, so an unconditional `S_IFREG` gate
would reject *every* file and silently revert agnos users to baked-in defaults. Both
verified in the vendored sources before writing the guard.

Verified after: all five paths return in 2–7 ms; regular files still read normally.

### A-02 — the watchdog abandons its budget when the child closes stdout and lives · HIGH

**Where**: [`src/shellout.cyr`](../../src/shellout.cyr).

The read loop has three exits and only one — the deadline — killed the child. This
finding is the one P-05 (below) missed by generalising from the case it tested.

On the **EOF exit** (`n <= 0`) the child may still be alive: a child that closes or
redirects its stdout and then keeps running hits it. The parent then goes straight to
`waitpid` on a live child, and **no deadline covers that** — the budget is enforced by
`epoll_wait`, which we have already left. The `EPIPE` mechanism that rescues the
buffer-full case does nothing here, because the child is not writing and never notices
the closed pipe.

**Failure scenario**: a fake `cyrius` on `PATH` (threat position 3) doing
`exec 1>&-; sleep 30` parked the prompt for the full **30 s against a 5 ms budget** —
measured at 12 s before my own test timeout cut it short.

**Fix**: kill the child unconditionally before waiting. Once we have stopped reading, its
exit status is irrelevant — `stbuf` is discarded and the return value is decided by the
`timed_out` / `sys_err` flags — so there is nothing to lose by killing it and everything
to lose by waiting on it. `SIGKILL` on an already-exited child is a harmless no-op.
`timed_out` still decides the *return value*; it no longer decides whether we are willing
to hang. Verified: 12,000 ms → 3 ms, with the buffer-full path still 5 ms. Pinned by
`test_shellout_eof_with_live_child_does_not_hang`.

### A-03 — the CI lock guard was inert · HIGH

**Where**: [`scripts/lock-check.sh`](../../scripts/lock-check.sh),
[`.github/workflows/ci.yml`](../../.github/workflows/ci.yml).

The guard added earlier the same day snapshotted `cyrius.lock` from the **working tree**.
But `ci.yml` runs a `Resolve dependencies` step (`cyrius deps`) *before* it, which
overwrites that file — so the guard compared a fresh resolution against another fresh
resolution. Identical by construction, **always exit 0**.

**Failure scenario, executed**: a lock committed with a `path` override active (zero
`commit` lines — the exact case the guard exists to catch) was reported
`lock-check: OK` with the CI step order as written.

**Fix**: take the baseline from `git show HEAD:cyrius.lock` — the *committed* state —
so the check is independent of what earlier steps did to the working tree and cannot be
defeated by reordering. Falls back to the working tree outside a git checkout. Verified:
a genuinely committed bad lock is now caught (`rc=1`, pin branch) *with* `cyrius deps`
still running first. This also fixes the separate report that `--no-resolve` compared the
file against itself.

### A-04 — bash reconstructs ESC from bytes the sanitizer deliberately let through · HIGH

**Where**: [`adapters/bash.sh`](../../adapters/bash.sh).

A second, independent channel from P-01, and **not** closed by `shopt -u promptvars`:
bash's prompt backslash decoding is unconditional.

`cmdrs` strips control *bytes*, correctly. But `\` and `e` are printable, so a repo
shipping `.python-version` containing the six characters `\e[31m` passes F-1 untouched —
and bash's decoder then turns `\e` into a real ESC (0x1b) and `\a` into BEL (0x07)
*inside the shell*. The sanitizer is bypassed by reconstructing the control byte on the
far side of it.

**Verified**: `cmdrs` emitted `v \ e [ 3 1 m R E D \ a` with no `033` or `007` anywhere;
after `${PS1@P}` the same string contained `033 [ 3 1 m` and a BEL.

**Fix**: double `\` → `\\` on the rendered bytes, so the decoder emits one literal
backslash and the escape never forms. The `\001`/`\002` readline markers are raw control
bytes, not backslash sequences, so they are unaffected. Verified after: the attacker's
`\e` stays literal while commandress's own SGR still renders.

### A-05 — the sanitizer passed UTF-8-encoded C1 controls · MEDIUM

**Where**: [`src/color.cyr`](../../src/color.cyr) `sanitize_segment_output`.

The filter dropped bytes `< 0x20` and `0x7F` and let everything `>= 0x80` through, on the
stated reasoning that high bytes are UTF-8 continuation bytes rather than controls. True
of the **bytes**, false of the **codepoints**: U+0080–U+009F is the C1 control set, and a
UTF-8 terminal that honours C1 reads U+009B as CSI and U+009D as OSC — precisely the
sequences F-1 exists to stop, smuggled past it two bytes at a time.

**Verified**: `\xc2\x9b31mRED\xc2\x9d0;title\xc2\x9c` reached stdout byte-for-byte.

**Fix**: drop `0xC2` followed by `0x80–0x9F`. `0xC2` followed by `0xA0–0xBF` is ordinary
Latin-1 punctuation and stays. Verified both directions: C1 pairs stripped, while `é`
(`c3 a9`) and NO-BREAK SPACE (`c2 a0`) survive. Pinned by two tests.

### A-06 — the config-warning path echoed raw config bytes · MEDIUM

**Where**: [`src/config.cyr`](../../src/config.cyr) — the unknown-field warning.

The sibling of P-02, at the site P-02 did not reach. `warning: unknown config field
'<key>' in [[<section>]]` wrote both values straight to stderr. These are `(ptr, len)`
pairs (`str_data`/`str_len`), not NUL-terminated cstrings, so they could not use the
cstring sanitizer — which is why they were missed.

**Fix**: `eprint_sanitized(buf, len)`, a length-aware twin of the filter that builds one
filtered copy and does one write. Verified: ESC in a config key no longer reaches the
terminal.

### A-07 — a right-prompt parse error rendered the LEFT prompt · MEDIUM

**Where**: [`src/cli.cyr`](../../src/cli.cyr) `cli_side_for` — a defect introduced by the
1.1.5 cmdit adoption.

The degrade policy returned `0` for *any* non-OK parse result, which degraded the **side**
as well as the exit code — two different things. `cmdrs --side=right --bogus` therefore
rendered the left prompt, and the zsh adapter runs
`RPROMPT="$($_CMDRS --side=right)"` — so one stray flag pasted the entire left prompt,
trailer and all, into the right prompt.

**Verified**: `--side=right` printed the time segment; `--side=right --bogus` printed
`/tmp  L ` instead.

**Fix**: cmdit stores each flag's value as it parses, so a `--side` that parsed cleanly
before an unrelated flag failed is still there to read. The contract is "never exit
non-zero and never blank the prompt" — it was never "discard input we successfully
understood".

**Note on the 1.1.5 tests**: they covered `--side=bogus` and `--nope` *alone*, both of
which correctly yield the left prompt — but that is just the default, so they passed for
the wrong reason. The combination was untested. Now pinned by
`test_cli_side_survives_an_unrelated_parse_error`.

### A-08 — `vcs_render`'s stack frame exceeds the entire agnos init stack · MEDIUM

**Where**: [`src/segments/vcs.cyr`](../../src/segments/vcs.cyr).

A 4 KB cwd buffer plus an 8 KB capture buffer make a **12,416-byte frame** — confirmed by
disassembling the agnos binary (`sub $0x3080,%rsp`, the largest frame in it). AGNOS hands
ring-3 only ~12 KB of init stack, so the frame alone is at or over the whole budget.
`lib/io.cyr::getenv` carries the identical guard for the identical reason and cites the
crash it caused (agnoshi_147 #PF, Cyrius CHANGELOG 6.1.12).

An early `return 0` would not have helped: a `var[]` in a statically-dead region still
reserves its stack at the prologue. The declaration has to be preprocessed away.

**Fix**: `#ifdef CYRIUS_TARGET_AGNOS return 0; #endif` before any declaration, with the
host body inside `#ifndef`. Nothing is lost — every input the function needs is already
stubbed on agnos (`cmdrs_getcwd` → 0, `shellout_capture` → -1, cache disabled), so the
host path could only ever have returned 0 there. Verified: largest agnos frame drops
**12,416 → 8,320 bytes**; host `vcs` behaviour unchanged.

### A-11 — a symlinked cache directory defeated the F-3 ownership gate · MEDIUM

**Where**: [`src/cache.cyr`](../../src/cache.cyr) `cache_init`.

F-3 verifies the cache dir is ours and `0o700` — but it used `stat`, which **follows
symlinks**. A co-tenant who wins the race to create `/tmp/commandress-<uid>` as a symlink
pointing at another directory we own with mode `0o700` (say `~/.ssh`) passes both checks,
and `cmdrs` then creates and renames files inside a directory of *their* choosing. The
`mkdir` fails with `EEXIST` in that case, so the stat was the only thing in the way.

**Fix**: `lstat` (via an agnos-safe `_cache_lstat` bridge — agnos exposes no `sys_lstat`
at all, so naming it unguarded fails the `--agnos` build even on an unreachable line),
plus an explicit `S_IFDIR` gate rather than relying on the coincidence that Linux gives
symlinks mode `0777`.

**Verified**: normal operation still creates and populates `/tmp/commandress-<uid>`
(`drwx------`, `vcs-077ebd41`); with the directory replaced by a symlink to an
attacker-chosen `0700` target, **0 files** are written and the cache disables.

### A-12 — the cache TTL check was one-sided · LOW

**Where**: [`src/cache.cyr`](../../src/cache.cyr) `cache_get`.

`now - mtime > ttl` never fires for an mtime in the **future** (the difference is
negative), so such an entry counts as fresh forever. Reachable with no attacker at all:
any backwards clock step — NTP correction, suspend/resume, a VM restored from a snapshot —
pins entries written "in the future" for the life of the file. **Fix**: treat
`mtime > now` as a miss.

### A-09 / A-10 / A-13 — CI least-privilege and pipeline hygiene · LOW

- **A-09**: `permissions: contents: write` sat at the **workflow** level in
  `release.yml`, so the CI-gate job inherited it — a job that builds, tests, and pipes a
  remote installer to `sh` held a token that could push to the repo. Moved to the release
  job alone; the workflow default is now `contents: read`.
- **A-10**: `softprops/action-gh-release@v2` is a **mutable tag** on the one step holding
  that write token. Pinned to the commit SHA it resolved to (`3bb1273…`).
- **A-13**: workflow pipelines ran without `pipefail`, so `cyrius bench | bench-gate.sh`
  reported the gate's status alone — a bench that emitted a valid line and *then* died
  would read green. `set -o pipefail` added; verified it turns that case red.

### P-07 — CI fetched an executable installer from a moving branch · MEDIUM

**Where**: [`.github/workflows/ci.yml`](../../.github/workflows/ci.yml),
[`.github/workflows/release.yml`](../../.github/workflows/release.yml).

Both workflows ran:

```sh
curl -sSf https://raw.githubusercontent.com/MacCracken/cyrius/main/scripts/install.sh | sh
```

The toolchain *version* was correctly pinned from `cyrius.cyml` — but the **installer
itself** was fetched from `main`, an unpinned moving target, and piped straight to `sh`.
Every CI run therefore executed whatever that branch said at that moment, on a runner
holding the workflow token; `release.yml` runs with `contents: write`.

**Fix (v1.1.6)**: fetch the installer from the pinned version tag —
`.../cyrius/$CYRIUS_VERSION/scripts/install.sh` — so the installer matches the toolchain
it installs and a change to `main` cannot alter our builds. Verified the tag URL resolves
(HTTP 200, 44,007 bytes at `6.5.35`).

**Residual risk, stated rather than hidden**: git tags are mutable, so a force-pushed
tag would still move under us; a commit SHA would be immutable. The tag is the same
trust level the `[deps.*]` pins already use, and it is a large improvement over `main`.

### P-04 — `cache_put` published short writes as complete entries · MEDIUM

**Where**: [`src/cache.cyr`](../../src/cache.cyr) — `cache_put`.

F-5 made cache writes atomic via temp+rename, and that holds. But **atomicity is not
integrity**: the result of `file_write(fd, value, value_len)` was discarded, so a short
write was `rename`d into place as though complete, and `cache_get` has no way to detect
it. The next redraw then renders a clipped branch name from cache for the whole TTL.

**Fix**: verify the byte count; on a short write, unlink the temp and return without
renaming, so a failed write degrades to a cache **miss** (correct, merely uncached)
rather than a wrong hit.

### P-02 — the unknown-segment warning re-emitted unsanitized bytes to the terminal · LOW

**Where**: [`src/render.cyr`](../../src/render.cyr) — the `fp == 0` branch.

Segment *output* is sanitized at the chokepoint one branch below; the segment **name**
echoed by `warning: unknown segment '<name>'` was not. Verified with a config naming a
segment `\x1b[31mBADSEG\x1b[0m`: the raw `033` bytes reached the terminal.

The name comes from the config file, which the F-1 analysis classifies as trusted, so
this sits inside the documented trust boundary and is rated LOW. It is still worth
closing: the warning fires **once per redraw for as long as the typo stands**, and
stderr is not captured by `PROMPT="$(cmdrs)"`, so it reaches the terminal directly
rather than the prompt string.

**Fix**: route the name through `sanitize_segment_output`. Verified: ESC bytes stripped.

### P-03 — every stdout write discarded its result · LOW

**Where**: [`src/render.cyr`](../../src/render.cyr) — 8 call sites.

All emits were bare `syscall(SYS_WRITE, STDOUT, buf, len)` with the result thrown away,
which assumes `write(2)` is all-or-nothing. A signal arriving mid-write returns `-EINTR`
having written nothing, and the render would report success on a truncated prompt.

**Rated LOW, deliberately.** The tempting framing is that pipe writes above `PIPE_BUF`
(4096) short-write and `cmdrs` writes into a pipe by construction — but for a *blocking*
fd the kernel writes everything, blocking as needed. Testing bore that out: a
60,000-byte prompt through a pipe, including through a deliberately slow reader,
delivered all 60,015 bytes both before and after the fix. The realistic trigger is
EINTR, not routine pipe behaviour. This is hardening, not a live defect.

**Fix**: a `_emit(buf, len)` helper that loops on partial writes and retries `-EINTR`,
treating a 0 return on non-zero length as a hard failure so it cannot spin. All 8 sites
routed through it. No measurable cost: `render_prompt` benches 10.976 µs, inside the
10.58–10.98 µs spread measured across the session.

### P-06 — the sanitization chokepoint could wild-write on allocation failure · LOW

**Where**: [`src/color.cyr`](../../src/color.cyr) — `sanitize_segment_output`.

stdlib `alloc` **returns 0** on failure (OOM, or a size outside `(0, ALLOC_MAX]`) — it
does not abort. Unguarded, the copy loop would `store8` from address 0 for every byte of
the input. Reachable only under genuine heap exhaustion, hence LOW — but this is the one
function every segment's output crosses on its way to the terminal, and a prompt renderer
that segfaults takes the user's shell prompt with it.

**Fix**: return 0 on a failed allocation, which is already the "nothing to paint"
contract `render_prompt` handles. Same defence cmdit itself added for `cmdit_new` in its
1.2.4 security release.

### P-08 — commandress depended on a private cmdit symbol · LOW

**Where**: [`src/main.cyr`](../../src/main.cyr) — `_print_help`.

The 1.1.5 CLI adoption called `_cmdit_eprint`. That is an underscore-prefixed **internal**
helper, not one of cmdit's 54 public `cmdit_*` entry points, so it sits outside the frozen
1.0.0 API that [ADR 0008](../adr/0008-cli-parsing-via-cmdit.md)'s tag pin is predicated on.
cmdit may rename or drop it in a patch release without that counting as a break, and our
build would fail on a routine pin bump — for a two-line helper we can own.

**Fix**: a local `_eprint`. `src/` now references only public `cmdit_*` names.

### P-05 — the shellout buffer-full path is safe, for one non-obvious reason · INFO

**Where**: [`src/shellout.cyr`](../../src/shellout.cyr).

> **Corrected by A-02.** This entry's conclusion — "the buffer-full path is safe" — is
> accurate. The generalisation it invited, that the function as a whole could not hang,
> was **wrong**: the EOF-with-live-child exit could and did, and A-02 found it. Recorded
> in full rather than quietly amended, because the *shape* of the mistake is the
> instructive part: a passing test on one exit path was taken as evidence about a
> function with three. The fix in A-02 (kill unconditionally) subsumes this one, and the
> ordering below is now belt-and-braces rather than the sole defence.

Opened as a suspected deadlock and refuted for the case tested, but the reason it is safe
was undocumented and unpinned, so it is recorded here.

When a child writes more than the capture buffer holds, the read loop exits with
`timed_out == 0`, so the child is **not** SIGKILLed — and it may still be writing. Once
the 64 KB pipe buffer fills it blocks in `write()`. Waiting on it while still holding the
read end open would block both sides forever and hang the user's prompt, which no deadline
covers: the parent is parked in `waitpid`, not in `epoll_wait`.

It does not hang because **`sys_close(rfd)` runs before `sys_waitpid`**. Closing the last
read end makes the child's next write fail with `EPIPE`/`SIGPIPE`, so it dies and the wait
reaps it immediately.

**Verified both directions.** As shipped: a child flooding 200 KB through a 256-byte
buffer returns in **5 ms**. With the two lines swapped in a scratch copy: the suite
**hangs** and is killed at 45 s. The invariant is now stated in the source at the
call site and pinned by
`tests/commandress.tcyr::test_shellout_oversized_child_does_not_hang`, which fails if the
ordering is reversed.

## Verified clean

Claims that were tested and held. Recording these matters as much as the findings — the
previous audit's mitigations are load-bearing and this is the evidence they still work.

- **F-1 ANSI sanitization holds at the chokepoint.** A hostile project shipping
  `.python-version` = `3.11\x1b[31mPWNED\x1b]0;title\x07`, `.nvmrc` = `20\x1b[2J`, and
  `rust-toolchain` = `stable\x1b[5m` rendered with every `033` and `007` stripped; the
  only ESC bytes in the output were commandress's own SGR. `$VIRTUAL_ENV` with an
  embedded ESC likewise stripped.
- **F-7 bounded exit parse holds.** `AGNOSHI_LAST_EXIT` across `0`, `42`, 21 nines,
  `-1`, `abc`, empty, `1e9`, `0x41`, `"  7  "`, and 5,000 nines: every malformed value
  rejected, none crashed, none hung.
- **Config parser is robust.** Empty file, truncated EOF, unterminated string, 500-deep
  nesting, a 200,000-character line, embedded NULs, 5,000 segments, and 4 KB of binary
  garbage: all `rc=0`, no crash, no hang.
- **`bench-gate.sh` does not false-pass.** Over-budget in µs and ms, missing
  `render_prompt` line, empty input, garbage unit, missing `avg` keyword, negative value:
  all correctly rejected; valid input with the 6.5.x timer-floor line correctly accepted.
- **`cache_get`'s stat→open TOCTOU is benign.** The read is bounded by the stat's
  `st_size` into an `st_size + 1` buffer, so a file that grows between the two cannot
  overflow it, and one that shrinks just reads short. The F-3 mode+uid gate means only
  our own UID (or root) can swap the file at all.
- **`shellout_capture` leaks no fds.** Every parent exit path closes `ep` and `rfd` and
  reaps the child; the child closes `rfd` and its `devnull` after `dup2`.
- **Oversized probe files degrade safely.** 100 KB `.python-version` / `.nvmrc` are
  capped at 256 bytes by `read_trimmed_file_at`; a 600-deep directory tree walks without
  incident; a `getcwd` beyond 4096 bytes renders the segment empty rather than truncating
  into a fixed buffer.

## Confirmed but deliberately not fixed

Findings the sweep confirmed, which were judged not worth changing now. Recorded so the
next audit revisits a decision rather than rediscovers a bug.

- **Config-derived `separator` / `trailer` / powerline glyph are emitted unsanitized**
  (`src/render.cyr`). Unlike the two *warning* paths (P-02, A-06), which echo content the
  user never intended as prompt output, these are deliberate prompt content from the
  user's own file — the trust boundary F-1 documents. Sanitizing them would also cost a
  filter pass per redraw on the hot path. Left as-is, consistent with the documented
  boundary.
- **`cmdit_argv`'s failure return is unchecked** (`src/main.cyr`). If the process argv
  cannot be read, `--side=right` silently becomes the left prompt. The only way argv is
  unreadable is a `/proc` failure that would break far more than the prompt.
- **`find_ancestor_with` is O(path_len × depth) with no depth cap**, repeated once per
  env segment. A 600-deep tree walks without incident (measured); `getcwd`'s 4096-byte
  buffer is the effective bound.
- **`cache_put` hardcodes syscall 82 for `rename`**, which on agnos is `SYS_GPU_DISPATCH`
  — a memory-writing matmul. Unreachable: `cache_init` disables the cache on agnos before
  any of this file's raw syscalls run, and the file header says so. Left as a comment
  rather than a code change, but worth knowing the number is not portable.
- **`bench-history.sh` would write a whole bench line into the `iters` column** if a line
  ever lacked its `[N iters]` suffix. No current harness output does.

## Known gaps, stated rather than hidden

- **A hostile repo can still put ~255 printable characters into the prompt** via a
  language-env probe file. Sanitized and inert, but visually disruptive on every redraw.
  `max_length` applies to `cwd` only. Not fixed: a per-segment length cap is a config
  schema addition, which is additive-only work under ADR 0007 and belongs in a feature
  release, not an audit patch.
- **`alloc` returns are unchecked elsewhere in `src/`.** P-06 guards the one chokepoint
  every segment crosses. The remaining sites allocate small, fixed-shape buffers and are
  reachable only under heap exhaustion; spraying guards through all of them was judged
  churn rather than hardening. Recorded so the next audit can revisit rather than
  rediscover.
- **Cache keys are a 32-bit djb2 of the cwd**, so two directories can in principle share
  an entry and render each other's branch name for one TTL second. Not exploitable
  across a privilege boundary (the cache is 0700 and per-UID) and not fixed.
- **Tag mutability** in P-07's fix, as noted there.
